# Docs, screenshots and the project site

## What

Make grofe presentable as a FOSS project, with every piece generated or
checked by a `just` recipe and a GitHub Actions job so nothing drifts:

1. **README**, rewritten short (aim: under 150 lines): one-line pitch, a
   light/dark screenshot (`<picture>` with `prefers-color-scheme` sources),
   install, a 30-second quickstart, "switching from tmux" in a few lines,
   and links to the docs site. Everything longer moves into the book.
2. **Screenshots** generated by `vhs` tapes (`docs/tapes/`), one tape run
   in a light and a dark theme. They are built by the Pages workflow and
   served from the site; the README references them by their Pages URL
   (`https://termage.github.io/grofe/img/...`), so no PNGs are
   committed and none go stale.
3. **mdBook docs** in `docs/book/` (mdBook is the Rust ecosystem standard).
   Human-written, concise guide pages: introduction, install, getting
   started, switching from tmux (incl. running grofe as `tmux`),
   configuration (TOML), framed panes, scratchpads, agent sessions,
   messages and the prompt, plugins, troubleshooting. Content comes from
   the current README and the code; do not invent behaviour.
4. **Generated reference**: `options.md` listing every built-in option
   with its TOML key (`src/config/mod.rs` mapping), tmux name, scope,
   type, default, allowed values and a one-line description. Each
   `Builtin` in `src/server/dispatch/options.rs` gains a `doc` field;
   write accurate descriptions (tmux's man page for tmux options, the
   grofe source for grofe's own). The generated file is committed and a
   test fails when it differs from what the table produces (bless with an
   env var, e.g. `GROFE_BLESS=1`), and a test fails if any option has an
   empty `doc`. If the command parser has a usage table, generate a
   commands reference the same way; if not, skip it.
5. **Landing page**: one hand-built `site/index.html` (inline CSS, no JS
   framework; a small inline script adds the theme toggle, GitHub stats and
   the agent demo, and the page works without it; light and dark via
   `prefers-color-scheme`, works at phone width): pitch, screenshots, install, links to docs and repo.
6. **Pages workflow** `.github/workflows/pages.yml`: on push to main build
   grofe, render the tapes (install vhs, ttyd, ffmpeg and a Nerd Font so
   the pill glyphs render), build the book, assemble `_site/` (landing at
   root, book under `/docs/`, images under `/img/`) and deploy with
   `actions/deploy-pages`. On pull requests it builds everything but does
   not deploy.
7. **justfile recipes**: `just docs` (regenerate reference + build book),
   `just docs-serve`, `just screenshots`, `just site` (assemble `_site/`
   locally exactly as CI does).

## Why

The user wants grofe to be a proper FOSS project others can adopt. Today
the README is 470+ lines mixing pitch and manual, `docs/` holds only
internal specs and plans, and the 165 options are documented nowhere.

## Acceptance criteria

- `just check` exits 0 (fmt, clippy, tests, bats), including the new
  reference-drift and non-empty-doc tests.
- `just site` builds `_site/` locally with `index.html`, `docs/index.html`,
  `docs/reference/options.html` and both theme screenshots.
- The README CI job (`readme.yml`, the `readme-test` blocks) still passes;
  keep tested blocks working.
- `pages.yml` succeeds on the PR (build only).
- README renders correctly on GitHub (images resolve once Pages deploys
  after merge; say so in the PR).
- No em dash as a sentence break anywhere; no hostnames, emails or
  machine specifics in shipped files.

## Do not build

- No publishing of `docs/specs` or `docs/plans` (internal).
- No docs framework other than mdBook; no JS on the landing page beyond
  the inline script for the theme toggle, GitHub stats and agent demo, each
  degrading without JS; no analytics.
- No packaging or release changes (separate PR, `feat/packaging`).
- Do not enable GitHub Pages in repo settings; that is done at merge.
