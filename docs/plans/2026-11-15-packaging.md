# Packaging and the v0.2.0 release pipeline

## What

Every artifact built and published by CI from a `v*` tag, each step also
runnable locally through a `just` recipe:

1. **Cargo metadata** for crates.io: description, repository, homepage
   (`https://morrieinmaas.github.io/grofe/`), readme, keywords,
   categories, and `include`/`exclude` so the package holds only what a
   build needs. `cargo publish --dry-run --locked` passes in CI on PRs.
2. **.deb and .rpm** for the two Linux musl targets (x86_64, aarch64) via
   `cargo-deb` and `cargo-generate-rpm` metadata in `Cargo.toml`, built in
   `release.yml` and attached to the GitHub release with `.sha256` files,
   next to the existing tarballs.
3. **CHANGELOG.md** generated by `git-cliff` (`cliff.toml`, conventional
   commits grouped by type) with a `v0.2.0` section. The release notes of
   a tag are that tag's CHANGELOG section, not `--generate-notes`.
4. **`just release <version>`**: bumps `Cargo.toml` (and `Cargo.lock`),
   regenerates the changelog, commits `chore(release): v<version>` and
   creates the tag locally. It never pushes; the user pushes the tag.
5. **Homebrew tap**: `packaging/homebrew/grofe.rb.tmpl` rendered with the
   release's four tarball URLs and sha256s (macOS arm64/x86_64, Linux
   arm64/x86_64) and pushed as `Formula/grofe.rb` to
   `morrieinmaas/homebrew-tap` by a `release.yml` job using the tap's
   write deploy key, secret `HOMEBREW_TAP_DEPLOY_KEY`. The job is skipped, not failed, when the secret
   is absent.
6. **AUR `grofe-bin`**: `packaging/aur/PKGBUILD.tmpl` rendered from the
   release (x86_64 and aarch64 tarballs, sha256s), `.SRCINFO` generated,
   pushed to `ssh://aur@aur.archlinux.org/grofe-bin.git` with secret
   `AUR_SSH_PRIVATE_KEY`. Skipped when the secret is absent.
7. **crates.io** publish job using trusted publishing
   (`rust-lang/crates-io-auth-action`), gated on repo variable
   `CRATES_IO_TRUSTED == 'true'` because the first publish is manual.
8. `just pkg-render <version>` renders the formula and PKGBUILD for an
   existing release into `target/pkg/` so they can be tested locally.
9. Releases are normal (not pre-release) from v0.2.0 on, so
   `releases/latest` points at them.
10. `RELEASING.md`: the one-time setup (crates.io first publish and
    trusted publisher, tap repo + token, AUR account + key, secrets and
    variable names) and the per-release steps.
11. README Install section gains the brew/AUR/cargo/deb/rpm lines. Touch
    only that section (another PR rewrites the rest of the README; merge
    `origin/main` before finishing and resolve carefully).

## Why

The user wants grofe installable the way FOSS tools are: Homebrew, AUR,
crates.io and Debian/Fedora packages, all published by CI/CD from the
GitHub release so nothing is maintained by hand.

## Acceptance criteria

- `just check` exits 0.
- `cargo publish --dry-run --locked` succeeds.
- `just pkg-render 0.1.0` renders a formula and PKGBUILD for the existing
  v0.1.0 release with correct sha256s.
- In an `archlinux` container (podman), `makepkg` builds and installs the
  rendered `grofe-bin` from v0.1.0 and `grofe -V` runs.
- In a Linux container, the rendered formula passes `brew style` /
  `brew audit --formula` (a Homebrew container image), or the closest
  available check, stated in the PR.
- `.deb` installs in a `debian:stable-slim` container and `.rpm` in
  `fedora` (built locally or in a test workflow run), `grofe -V` runs.
- `release.yml` is valid (`actionlint` clean) and its new jobs skip
  cleanly without secrets.
- No em dash as a sentence break; no AI attribution; no machine
  specifics in shipped files.

## Do not build

- No tag push, no real release, no repo creation, no secrets, no first
  crates.io publish: those happen at the merge gate with the user.
- No COPR, Nix or Debian-official packaging.
- No README changes outside the Install section.
